## Mission

> Help people manage their agentic resources — skills, agents, and rules — the AI Era's most important building blocks for crafting an AI world of their own.

This is the core mission, and every ship serves it. In the AI Era, agentic resources are the fundamental units of capability: the more cleanly a person can collect, organize, and project them across tools, the more freely they can shape AI to their own intent. Agentic Hub exists to make those building blocks first-class, safe to manage, and effortless to move — so the user, not the tooling, owns the AI world they build.

Every feature in this document is a means to that end. If a feature does not help someone better manage, control, and craft with their agentic resources, it does not belong here.

## Overview

Agentic Hub is a Tauri 2.x desktop app that lets a power user manage shared agentic capabilities — `skills`, `agents`, and `rules` — across multiple AI coding tools (Codex, Claude Code, Cursor, OpenClaw, and the OpenStandard `~/.agents` root) from one place. It scans a single shared root (`~/.agentic` by default), shows what is enabled per tool, lets the user stage and apply safe filesystem projection changes, and supports named suites and per-project workspace patches for one-click scenario switching.

This product is a migration of the Unified Agentic Capability Manager originally shipped as a VS Code extension feature inside `e-studio-copilot`. The product semantics, filesystem contracts, and projection rules are preserved 1:1. The host changes from a VS Code webview to a standalone Tauri 2.x desktop window with a Rust core for filesystem operations and a React + Vite + TypeScript UI.

## Problem

Power users of agentic AI tools collect skills, agents, and rules across many tools. Today this leads to three concrete pains:

1. **Drift between tools.** A useful skill in Cursor needs to be copied or symlinked into Claude Code, Codex, and OpenClaw to take effect. Each tool has different scan paths, layout rules, and instruction-file conventions. Keeping them in sync by hand is slow and error-prone.
2. **No safe batch control.** Existing workflows depend on bash scripts, ad-hoc symlinks, or per-tool dotfile edits. There is no way to see what is enabled across tools, replace a broken symlink, or refuse a destructive overwrite without writing custom code per operation.
3. **No scenario switching.** Users want different capability sets for coding, research, writing, and per-project work. Today this requires re-toggling dozens of items or maintaining parallel directory trees.

The VS Code extension solved this inside one editor. Agentic Hub generalizes the solution to a standalone app so it works regardless of which editor or terminal the user is in, including users who do not use VS Code at all.

## Target User

Primary user: one power user managing personal AI capabilities on one machine.

- Uses two or more of: Codex, Claude Code, Cursor, OpenClaw
- Already maintains a shared `~/.agentic`-style directory or is comfortable with local filesystem concepts
- Wants batch control and visibility across tools without writing bash glue
- Works across multiple project repos and wants per-project capability sets

Out of scope for now: teams, multi-machine sync, cloud profiles, organizational sharing.

## Scope

### In Scope

- Tauri 2.x desktop app with a main window (Agentic Capability Manager) and a secondary window (Suite Manager)
- Scan a configurable shared root (default `~/.agentic`) for `skills/`, `agents/`, `rules/`
- Five tool adapters: Codex, Claude Code, Cursor, OpenClaw, and OpenStandard (the open-standard `~/.agents` root, global-only)
- Per-tool projection of skills and agents using the existing layout strategies:
  - Claude Code: `flat` layout for **skills** (basename only at `~/.claude/skills/`; the skill loader is non-recursive). Claude **agents** are `nested` — the agent loader scans `~/.claude/agents/` recursively.
  - Codex, Cursor, OpenClaw, OpenStandard: `nested` layout (preserve category hierarchy)
- Per-tool rule projection modes:
  - `link_sync` (Cursor → `~/.cursor/rules`)
  - `markdown_section_sync` (Codex `~/.codex/AGENTS.md`, Claude `~/.claude/CLAUDE.md`, OpenClaw `~/.openclaw/workspace/SOUL.md`, OpenStandard `~/.agents/AGENTS.md`)
  - `file_sync` (supported model, not a default in v1)
- Stage-then-apply mutation model with a clear plan/result summary
- Safe filesystem semantics:
  - Replace wrong or broken symlinks
  - Refresh managed copies (Cursor agents) with stale detection
  - Never overwrite a real file or directory
  - Surface basename collisions in `flat` layout as `skip_conflict`
- Demo scaffold command that bootstraps `~/.agentic/` with starter skills/agents/rules on a fresh machine
- Suite Presets: named capability sets in `~/.agentic-suites.json`, applied as a full reset for one tool at a time
- Workspace Suite Sync: hard-copy a suite into a project workspace with a manifest cycle at `<ws>/.agentic-hub/workspace-patch.json`
- Persisted workspace target store (recent project dirs) with LRU eviction
- Settings persisted at `~/.agentic-hub/config.json`

### Out of Scope

- Code, build setup, or UI mockups for this doc pass — this PRD only defines the product surface
- VS Code extension parity for E-Studio remote-sync, markdown link navigation, slash commands, or file-context aggregation (those features stay in `e-studio-copilot`)
- Background filesystem watchers
- Multi-machine sync, cloud state, or shared suites across users
- Team-level capability libraries
- Workspace target for OpenClaw (matches existing VS Code scope decision)
- Per-tool overrides inside a suite definition
- Suite import/export, suite composition, suite versioning
- Auto-detection of installed tools
- Drift detection or watch-mode for workspace files
- Windows-first symlink behavior in v1 (macOS first, Linux follow-on, Windows documented as constrained — see `ARCHITECTURE.permissions.md`)

## User Stories

### P0 — Must Have

- As a power user, I want to open Agentic Hub and immediately see all my shared skills, agents, and rules for a selected tool, so that I know what is active without running terminal commands.
- As a power user, I want to stage enable/disable changes and apply them in one batch, so that I do not mutate disk file-by-file.
- As a power user, I want apply to safely create missing symlinks, replace wrong or broken symlinks, and refuse to overwrite real files, so that I cannot lose hand-edited content by accident.
- As a Cursor user, I want enabled agents to be written as managed file copies (not symlinks) and refreshed when the shared source changes, so that Cursor's runtime loader picks them up correctly.
- As a Claude Code user, I want my nested-category skills to project flat into `~/.claude/skills/` with basename-only targets, so that Claude's non-recursive skill loader actually discovers them (agents keep their nesting — Claude's agent loader is recursive).
- As a Claude Code user, I want basename collisions to surface as explicit conflicts I must resolve, so that two source skills with the same basename never silently overwrite each other.
- As a Codex / Claude / OpenClaw user, I want enabling a shared rule to write a managed marker-delimited block inside the right instruction file (`~/.codex/AGENTS.md`, `~/.claude/CLAUDE.md`, `~/.openclaw/workspace/SOUL.md`), so that the rule actually takes effect for that tool's next session.
- As a first-time user, I want a one-shot "scaffold demo resources" command that creates a starter `~/.agentic/` tree, so that I can use the app immediately on a fresh machine without copying a personal repo.
- As a multi-scenario user, I want to save a named suite (e.g. `coding-mode`, `research-mode`) and apply it to a tool as a full reset in one click, so that I switch context without re-toggling dozens of items.
- As a multi-project user, I want to apply a suite into a chosen project workspace as hard-copy files, so that Codex / Claude / Cursor pick up project-scoped capabilities without touching my global home.
- As a multi-project user, I want re-applying a different suite into the same workspace to clean the prior payload first, so that workspace state stays consistent with the manifest.

### P1 — Important

- As a power user, I want a search box that filters the visible capability list without rescanning, so that working in a large shared root stays fast.
- As a power user, I want a kind filter (all / skills / agents / rules), so that I can focus on one capability type at a time.
- As a power user, I want bulk "select visible / clear visible" actions, so that staging large changes is one click instead of many.
- As a Suite Manager user, I want "Create from current" to capture the currently enabled set for the focused tool as a new suite, so that I can codify a known-good configuration without re-typing every capability id.
- As a Suite Manager user, I want stale suite references (capabilities that no longer exist in the shared root) shown with a warning badge and skipped on apply, so that suites degrade gracefully when the shared root changes.
- As a workspace user, I want recently-used workspace directories listed with LRU ordering and a "Forget" action, so that I can switch between project workspaces quickly.

### P2 — Nice to Have

- As a power user, I want cross-tool read-only state inside the inspector (see which other tools have this item enabled), so that I can audit consistency at a glance.
- As a power user, I want a manual refresh that re-reads disk state on demand, so that I can resync after external file changes without restarting the app.
- As a Tauri app user, I want native menu items and keyboard shortcuts for common actions (refresh, apply, switch tool), so that the app feels native on macOS.

## Feature Specs

### 1. Capability Manager Main Window

**Story:** As a power user, I want one window that shows what is enabled per tool and lets me batch toggle.

**Description:** A single Tauri window with header (title, shared root display, scope toggle Global / Workspace, tool tabs, refresh, settings), body (searchable capability list on the left, inspector + staged operations preview on the right), and footer (staged count, apply changes, clear staged).

**Acceptance Criteria:**
- [ ] Window opens to the last-active tool tab and Global scope by default
- [ ] Header displays the resolved absolute shared root path
- [ ] Tool tabs include Codex, Claude Code, Cursor, OpenClaw, OpenStandard (Global) or Codex, Claude Code, Cursor (Workspace)
- [ ] Capability list groups by kind and shows per-item state (`enabled`, `disabled`, `broken`, `stale`, `foreign_file`, `foreign_link`)
- [ ] Search filters the visible list client-side without rescanning disk
- [ ] Staging a toggle does not mutate disk
- [ ] Apply runs the planner + applier and posts a result summary toast

**Edge Cases:** invalid shared root (missing or non-dir); tool unavailable (target path missing); permission denied during apply; collision on flat layout

**Dependencies:** Tauri IPC contract (`cmd_scan`, `cmd_inspect`, `cmd_plan`, `cmd_apply`, `cmd_sync_rules`), persisted settings, persisted workspace target store

### 2. Shared Root Scanner

**Story:** As a power user, I want my shared root scanned reliably with clear validation errors.

**Description:** Scan `<sharedRoot>/skills/`, `<sharedRoot>/agents/`, `<sharedRoot>/rules/` and produce a flat list of `CapabilityItem` records. A skill is valid if its path is a directory containing `SKILL.md`. An agent is a `.md` file. A rule is a `.md` or `.mdc` file. Invalid items are still listed but cannot be enabled.

**Acceptance Criteria:**
- [ ] Scan completes for typical shared roots (tens to low hundreds of items) under 200ms cold
- [ ] Nested category folders (e.g. `skills/dev/repo-research/`) are preserved in `relativePath`
- [ ] Symlinks inside the shared root are followed to their target for validation
- [ ] Validation errors are captured per item, not as a global scan failure
- [ ] Scan is triggered on window open and on manual refresh only — no background watcher in v1

**Edge Cases:** shared root is a symlink; shared root contains a large vendor folder (scan must constrain to expected directories); symlink cycles

**Dependencies:** `agentic-core::scanner`

### 3. Tool Adapter Registry

**Story:** As a power user, I want each tool's projection rules in one place so I can trust the behavior.

**Description:** Declarative per-tool adapter that owns target paths, projection kind per capability kind, and layout strategy. The full matrix lives in `docs/tech/reference/tool-adapter-matrix.md`. Adapter is the only code that decides basename-vs-relative-path.

**Acceptance Criteria:**
- [ ] Each adapter declares: `tool id`, `enabled` flag, `skillsPath`, `agentsPath`, `rulesPath`, `instructionsPath`, `skillLayout` (`flat`/`nested`), `agentLayout`, `ruleProjectionKind` (`link_sync`/`file_sync`/`markdown_section_sync`)
- [ ] If a tool target path is missing or inaccessible, the adapter reports a typed `tool_unavailable` error to the UI and no apply operations run for that tool
- [ ] All path resolution lives in the adapter — UI code and apply code never call `path.join` against tool-specific roots directly

**Edge Cases:** tool path is a symlink to a missing target; tool path lives inside the shared root by mistake

**Dependencies:** settings, scanner

### 4. Plan / Apply Engine

**Story:** As a power user, I want staged changes turned into an explicit plan I can trust to be safe.

**Description:** `Planner` reads current disk state per tool, diffs against the desired-state map, and emits a list of `PlannedOperation` records (`create_link`, `remove_link`, `replace_link`, `create_managed_copy`, `remove_managed_copy`, `replace_managed_copy`, `skip_conflict`). `Applier` executes the plan with safe semantics.

**Acceptance Criteria:**
- [ ] Correct existing symlink → no-op
- [ ] Broken symlink → `replace_link`
- [ ] Wrong-target symlink → `replace_link`
- [ ] Real file at target → `skip_conflict` with reason
- [ ] Real directory at target → `skip_conflict` with reason
- [ ] Cursor agents → `create_managed_copy` / `replace_managed_copy` instead of symlinks
- [ ] Managed copy whose sync metadata mismatches the shared source → `stale` state surfaced; refresh only on explicit apply
- [ ] Flat-layout basename collisions → `skip_conflict` (first-id-wins, lexicographic) with actionable reason
- [ ] Apply result returns counts: created, removed, replaced, refreshed, skipped, errors
- [ ] Partial apply is allowed: per-item failures do not abort the rest of the plan

**Edge Cases:** target parent directory missing (apply creates it for enabled tools); permission denied mid-apply; shared source removed between plan and apply

**Dependencies:** scanner, adapter registry

### 5. Rule Instruction Sync

**Story:** As a power user, I want enabling a rule to actually affect the tool's next session.

**Description:** For tools using `markdown_section_sync`, rewrite a single managed marker-delimited block inside the tool's instruction file. Strip YAML frontmatter from each rule body before inlining. Preserve all content outside the managed block. If no rules remain enabled for a tool, remove only the managed block. Delete the whole file only when the managed block was the entire file.

**Acceptance Criteria:**
- [ ] Marker contract: `<!-- agentic-hub:start -->` / `<!-- agentic-hub:end -->` (identical to the rebranded VS Code extension for migration parity)
- [ ] Codex rules sync to `~/.codex/AGENTS.md`
- [ ] Claude rules sync to `~/.claude/CLAUDE.md`
- [ ] OpenClaw rules sync to `~/.openclaw/workspace/SOUL.md`
- [ ] Rule body is inlined with frontmatter stripped
- [ ] Optional `Mirrored link:` annotation included only when a real mirrored file exists at the tool's `rulesPath`
- [ ] Malformed markers (start without end, or end before start) → `broken` state; no rewrite until fresh apply
- [ ] Target is a directory or non-file → reported as conflict, no write

**Edge Cases:** instruction file does not exist (created with managed block at top); file exists but lacks markers (block appended after existing content)

**Dependencies:** scanner, adapter registry

### 6. Demo Scaffold

**Story:** As a first-time user, I want a one-shot bootstrap that creates a sane `~/.agentic` tree.

**Description:** A Tauri command (`cmd_scaffold_demo`) and a UI affordance ("Scaffold Demo Resources" button in empty-state) that materializes a bundled template tree at the configured `sharedRoot`. Two modes: `merge` (write only missing paths) and `overwrite` (replace existing files with bundled copies).

**Acceptance Criteria:**
- [ ] Bundled content includes `README.md`, `ONBOARD.md`, demo skills (`e-studio-copilot-setup`, `npx-skills-workflow`), demo agent, demo rule
- [ ] `merge` mode never overwrites an existing file
- [ ] `overwrite` mode replaces files but does not delete user-added files
- [ ] After scaffold, an explicit user action (not the scaffold itself) is required to enable items into tools
- [ ] Result summary reports written / skipped / errors counts

**Edge Cases:** `sharedRoot` is a file (refused); permission denied; partial write failure (atomic per-file)

**Dependencies:** settings, bundled template embedded in the Tauri app resources

### 7. Suite Presets

**Story:** As a multi-scenario user, I want to save and apply named capability sets.

**Description:** A separate Suite Manager window for full CRUD on suites stored at `~/.agentic-suites.json`. A suite is a tool-agnostic list of capability IDs. Applying a suite to a focused tool is a full reset: every scanned item gets a desired state (`true` if in suite, `false` otherwise) and runs through the same plan/apply pipeline.

**Acceptance Criteria:**
- [ ] Suite Manager window opens via menu / button
- [ ] Suite list reads from `~/.agentic-suites.json`; missing file initialized as `{ "version": 1, "suites": [] }` on first write
- [ ] Create / Edit / Delete / Rename suite, with capability checklist sourced from latest scan
- [ ] "Create from current" pre-fills the checklist with the currently enabled set for the focused tool
- [ ] Stale capability references (in suite but not in scan) show a warning badge
- [ ] Apply suite triggers a confirmation dialog showing suite name and tool
- [ ] On apply: existing projections for the focused tool are reset, only suite items are enabled, rule sync runs for `markdown_section_sync` tools
- [ ] Apply result summary reports skipped-stale count
- [ ] Suite IDs are UUIDs (stable under rename); names must be unique at creation time
- [ ] Atomic dotfile writes via `<file>.tmp` + rename

**Edge Cases:** dotfile missing (created on first save); dotfile malformed (error surfaced, in-memory state preserved); empty suite apply (disables all — explicit confirmation message); concurrent panel writes (last write wins, acceptable in v1)

**Dependencies:** scanner, plan / apply engine, rule sync, suite store

### 8. Workspace Suite Sync

**Story:** As a multi-project user, I want to apply a suite into a project folder using hard copy.

**Description:** Header toggle switches between `Global` and `Workspace` scope. In Workspace scope, the user picks a workspace directory, selects a suite, selects a focused tool (Codex / Claude / Cursor only — OpenClaw not supported), and clicks Apply. The apply hard-copies skills, agents, and Cursor rules into per-tool workspace paths, writes managed markdown blocks for Codex/Claude rules, and maintains a manifest at `<ws>/.agentic-hub/workspace-patch.json` for the next clean cycle.

**Acceptance Criteria:**
- [ ] Header toggle: Global / Workspace, with Workspace tab visually distinct when active
- [ ] Workspace folder picker (Tauri dialog plugin) persists choices across app restarts with LRU ordering (cap 12)
- [ ] Tool tabs in Workspace scope are filtered to Codex, Claude, Cursor only
- [ ] Per-tool workspace targets:
  - Codex: `<ws>/.agents/skills/`, `<ws>/.codex/agents/` (subagent TOML), managed section in `<ws>/AGENTS.md`
  - Claude: `<ws>/.claude/skills/`, `<ws>/.claude/agents/`, managed section in `<ws>/CLAUDE.md`
  - Cursor: `<ws>/.cursor/skills/`, `<ws>/.cursor/agents/`, raw file copies at `<ws>/.cursor/rules/`
- [ ] Apply runs only after confirmation dialog showing workspace dir and suite name
- [ ] Prior manifest payload is cleaned (files removed, dirs pruned up to workspace root, managed block emptied) before new payload is written
- [ ] Re-apply with a different tool cleans the previous tool's payload (single-tool manifest)
- [ ] Out-of-workspace target paths refused as errors, not silently allowed
- [ ] Manifest written atomically via `.tmp` + rename
- [ ] Symlinks inside a shared skill directory are dereferenced and copied as their resolved file/dir contents (no symlinks cross the workspace boundary)
- [ ] Stale suite references skipped and counted in result summary

**Edge Cases:** workspace dir does not exist (refused); workspace dir is a file (refused); permission denied during clean or copy (partial apply allowed, errors reported)

**Dependencies:** suite store, plan / apply engine, rule sync, workspace target store

## Non-Functional Requirements

### Performance

- Cold scan of a 500-item shared root completes under 500ms on a 2020-era laptop
- Plan computation under 100ms for a typical desired-state diff
- Apply latency dominated by FS calls; surfaced via Tauri event channel so the UI can show per-operation progress
- App cold-start to first interactive window under 1.5s on macOS
- No background watcher in v1 — manual refresh and on-open scans only

### Security

- All filesystem mutations happen in the Rust core, never in the WebView
- Tauri 2.x capability model: scoped FS access to `~/.agentic`, `~/.codex`, `~/.claude`, `~/.cursor`, `~/.openclaw`, `~/.agentic-hub`, and user-picked workspace dirs (runtime scope additions via `fs:allow-*`)
- WebView never gets `shell:execute` capability
- All target paths normalized to absolute paths before validation
- Workspace patch refuses any resolved target that escapes the chosen workspace root
- See `ARCHITECTURE.permissions.md` for full trust-boundary model

### Reliability

- Plan and apply are idempotent against repeated runs
- Apply errors per-operation do not abort the rest of the plan
- Dotfile writes (`~/.agentic-hub/config.json`, `~/.agentic-suites.json`, `<ws>/.agentic-hub/workspace-patch.json`) use atomic `.tmp` + rename
- Markdown section sync preserves all content outside the managed marker block

### Observability

- Apply result summary always shown in the UI (counts + per-error reasons)
- Optional verbose log file at `~/.agentic-hub/log/agentic-hub.log` (rotating, capped at 10MB)
- Tauri DevTools available in dev builds only

### Deployment Constraints

- Ships as a Tauri 2.x desktop app
- Primary target: macOS (universal binary, distributed as `.dmg`)
- Secondary target: Linux (`.deb`, `.AppImage`)
- Windows: documented as constrained in v1 due to symlink permission model — see `ARCHITECTURE.permissions.md`. Managed-copy fallback path documented but not validated for v1 shipping
- No remote network calls in v1 (no telemetry, no auto-update endpoint pinging — auto-update via `tauri-plugin-updater` is a follow-on)

## Open Questions

- **Managed block markers.** Resolved: the (rebranded) VS Code extension uses `<!-- agentic-hub:start -->` / `:end` with the heading `## Agentic Hub Managed Rules`. Agentic Hub matches these verbatim so users migrate without touching their instruction files. The legacy `e-studio-*` names are not reintroduced.
- **Suite storage path.** Keep `~/.agentic-suites.json` (extension parity, portable across tools) or move to `~/.agentic-hub/suites.json`? **Default for v1: preserve `~/.agentic-suites.json`** for cross-app compatibility.
- **Workspace manifest folder.** Confirmed `<ws>/.agentic-hub/workspace-patch.json`. Gitignore guidance: document in README that this folder should typically be gitignored, but allow users to commit it if they want shared project-level capability state.
- **Windows symlink fallback.** Symlinks require either Developer Mode or admin elevation on Windows. v1 documents Windows as constrained. The `managed_copy` projection path technically works on Windows but has not been validated. Decide before any Windows release whether to ship at all or to skip.
- **Auto-update.** `tauri-plugin-updater` is supported in Tauri 2.x but requires hosting signed manifests. For v1, the app is unsigned / unhosted. Decide before public release.
- **Telemetry.** None in v1. Decide later if usage-pattern instrumentation is worth adding for personal-tool optimization.
- **OpenClaw workspace support.** Currently out of scope (matches VS Code decision). Revisit once OpenClaw's project-level scan path stabilizes.
